Cross-check: 160M requests × ~1s average wall-clock × 2 GB ≈ 89,000 GB-hours/month ≈ $940 — which matches the ~$960/month memory pace almost exactly.
Section 2 — Deep dive

Why each driver costs so much

Each driver below was verified directly in the codebase and the Vercel project configuration.

1. The engagement heartbeat verified in code

~55–65% of all requests

The embedded widget fires a POST /api/widgets/engagement ping every 30 seconds for every visible browser tab on every customer site (pixel-generator.ts:2446 — setInterval(sendHeartbeat, 30000)). A 5-minute visit produces ~10 pings. The server handler (src/app/api/widgets/engagement/route.ts) runs 3 database lookups plus an update per ping, and returns a JSON body the client never reads — it is pure fire-and-forget.

~10 pingsper 5-minute session
~90–105Mrequests/month across ~40 domains
~1s eachwall-clock on a 2 GB instance (DB waits)
~$550–750/moshare of memory + CPU + edge requests

2. Pageview deferred work keeps instances alive verified in code

multiplies billed seconds per pageview

src/app/api/widgets/pageview/route.ts (2,643 lines, maxDuration = 60) responds quickly, but then continues running heavy work inside Next.js after(). Vercel bills Provisioned Memory for the entire time the instance is alive — including everything after the response is sent:

  • Duplicate-contact sweep (:813) — finds and merges contacts created by concurrent handlers.
  • Fingerprint session linking (:277) — matches anonymous sessions by IP / device / city / OS.
  • Click-ID stitching (:406) — links sessions sharing the same gclid.
  • Conversion re-attribution loop (:531) — re-runs the AttributionEngine per conversion row from the last 30 minutes; the single most expensive block.

3. Widget script served through a function verified in code

millions of avoidable invocations/mo

Every customer page loads its tracking script from /api/widgets/[pixelCode]. That route performs a database check and regenerates the entire ~3,500-line script on every request, with an edge cache of only s-maxage=300 (5 minutes) and browser cache of 5 minutes. The script's content only actually changes when the app is deployed. Result: millions of function invocations per month that a longer cache lifetime plus an ETag/304 response would eliminate almost entirely.

4. 100 cron jobs verified in vercel.json

small $ (~$20–60/mo) but free to fix

vercel.json defines exactly 100 cron jobs — 2 run every minute, 23 run every 5 minutes, and 25 route patterns are granted an 800-second maxDuration. That is roughly 12,000 function invocations per day from schedules alone. In dollar terms this is a minor driver, because most jobs early-exit in under a second when there is no work — but every run also queries PlanetScale, so slowing them is a free win for database load (a stated priority for this stack) as well as a small Vercel saving.

5. The unaudited remainder needs a dashboard check

~$300–400/mo gap

The three verified line items extrapolate to ~$1,625/month, leaving roughly $300–400 unaccounted for against the ~$2,000 total. Likely composition, in order of probability given this traffic profile:

  • Observability Plus — $1.20 per million events. At 160M+ requests/month this alone could be $150–200+ if enabled without sampling.
  • Team seats — $20 per member; the repo shows at least 3–4 active committers.
  • Fast Data Transfer — response bytes across 160M requests.
  • Web Analytics / Speed Insights / Log Drains — per-event add-ons if enabled.
  • On-demand concurrent builds — only if enabled in Settings → Billing; at 30–60 builds/day it would be visible but modest.
Action: open vercel.com/agent-kong/~/usage and Settings → Billing, and read every remaining line item. This requires no code and may surface $100–300/month of instantly switch-off-able cost (observability sampling, unused add-ons).
Section 3 — The plan

Solutions, effort, and risks

Ordered by expected savings. Every solution lists what could go wrong and how to contain it — the tracking path carries customer revenue data, so nothing here ships without a canary and a rollback path.

1

Batch the engagement heartbeat client-side

saves ~$550–750/mo 1–2 days + 1 week soak medium risk, well mitigated

What changes

  • Keep the 30s timer in pixel-generator.ts, but accumulate locally (timeOnPage, scrollDepth, clicks) instead of sending.
  • Flush once via sendBeacon on pagehide / tab-hidden, plus a 5-minute fallback flush for long-lived tabs. ~10 pings/session drops to 1–2.
  • Server accepts the same payload (its existing Math.max merge already tolerates late/duplicate arrival), returns 204 No Content, gets maxDuration = 10.
  • Also audit the two other periodic senders found at pixel-generator.ts:2163 and :3249 for the same pattern.

Risks & mitigations

  • Data loss on browser crash / OS tab kill: the final beacon never fires, so that session's last interval of engagement is lost. Mitigation: the 5-minute fallback flush caps the loss window; final values are what dashboards use, and Math.max merging means partial data is never corrupting — only slightly stale.
  • This is the highest-traffic path — failures are not acceptable: the widget script propagates globally within ~5 minutes of deploy (5-min cache). Mitigation: ship behind a server-side flag in the generated script, canary on one pixel first, verify DB rows via PlanetScale, then ramp. Rollback = flip the flag; old behavior returns within 5 minutes.
  • Granularity loss: intermediate 30s-resolution engagement snapshots stop existing. Verified: no dashboard or live-visitor feature consumes intermediate values today — but this forecloses building a real-time "active visitors" feature later without revisiting.
  • sendBeacon payload limits (~64KB): current payload is tiny; batching adds a few fields. No practical risk, but enforce a size guard.
2

Move pageview after() work to a QStash worker

saves ~$150–250/mo net 2–3 days + regression tests medium risk

What changes

  • Replace the after() block (dedup sweep, fingerprint linking, gclid stitching, conversion re-attribution) with one QStash enqueue; a new worker route processes it in the background.
  • The QStash publish pattern already exists in this codebase (contact.router.ts, workers under src/app/api/qstash/) — copy it, don't invent it.
  • Pageview billed wall-clock drops from ~3–5s to ~0.5–1s per request.
  • This also aligns with the repo's own performance rule: "defer stitching/enrichment to background jobs."

Risks & mitigations

  • Compute moves, it doesn't vanish: the worker still runs the same logic on Vercel. Net win comes from batching per contact/session instead of per pageview, and shorter tail durations. QStash message cost (~$1 per 100k) is small but nonzero.
  • New failure surface: queue delivery, retries, and out-of-order processing can produce attribution races that after() never had. Mitigation: idempotent worker design, QStash deduplication keys, and regression tests against a 500k-pageview account before rollout.
  • Latency of attribution upgrades: conversions may show as Direct/Organic for seconds-to-minutes longer before re-attribution lands. Customer-visible only in near-real-time dashboard views.
3

Right-size function memory on widget routes (2 GB to 1 GB)

saves ~$100–200/mo hours low risk (sequenced after #2)

What changes

  • Provisioned Memory bills per GB — halving instance size on the highest-volume routes roughly halves their memory line.
  • Add "memory": 1024 in the vercel.json functions block for engagement, pageview, e, payment-link-click, and the script route. Only one route has any memory override today.
  • Verify the project's actual default in Settings → Functions first (dashboard-level setting is not visible in the repo).

Risks & mitigations

  • Out-of-memory on heavy requests: the 2,643-line pageview handler with its attribution loops may genuinely need headroom today. Mitigation: apply to pageview only after Solution 2 slims it; apply to the lightweight engagement/script routes immediately. Watch runtime errors via Vercel logs for 48h.
  • Slightly slower CPU allocation: smaller fluid instances get proportionally less vCPU; for I/O-bound handlers (these are), the latency impact is minimal.
4

Cache the widget script properly (ETag + longer s-maxage)

saves ~$30–60/mo hours low risk

What changes

  • Raise s-maxage from 300 to 3600 with stale-while-revalidate on /api/widgets/[pixelCode].
  • Add an ETag derived from the deploy/script version; return 304 Not Modified on match — skips DB check and regeneration.

Risks & mitigations

  • Slower propagation of widget changes: script updates (including the Solution 1 rollout flag) take up to 1 hour to reach all visitors instead of 5 minutes. Mitigation: ship this after the heartbeat canary is complete, or use a 900s compromise during the rollout window. This is an explicit decision item below.
  • Disabled-pixel lag: a deactivated pixel keeps serving for up to the cache TTL. Acceptable for a tracking script; note it in support docs.
5

Slow 20 cron jobs (26 one-line schedule edits)

saves ~$15–40/mo + DB load minutes to edit, days to observe low risk for the 20 listed

The main risk of slowing any reconciliation job is reduced freshness granularity — data that arrives only via polling shows up 5–10 minutes later on average in customer dashboards.

Invoice audit — no code required

potentially $100–300/mo 30 minutes in the dashboard no risk

What to check

  • Read every remaining line item on the usage page (the ~$300–400/mo gap).
  • If Observability Plus is large: exclude/sample the widget routes — they generate the events but nobody debugs them per-request.

Decision checklist

1. Approve heartbeat batching with canary rollout?

2. Script cache TTL: 1 hour or 15 minutes?

Booking notifications, Meta CAPI retry, agent replies, billing charges, wallet suspension.

Keep full events on webhook/conversion money paths.

Recommended: yes, if the audit shows >$50/mo

6. QStash migration of pageview after() work?

Highest engineering risk of the set; requires attribution regression testing on a 500k-pageview account.

Recommended: yes, sequenced after 1–5 land

Methodology & assumptions

  1. Verified facts come from: the Vercel usage dashboard (line-item dollars, read by the team), the Vercel API via MCP (projects, domains, deployment volume), and direct code inspection (heartbeat interval, cron schedules, function config, route handlers).
  2. The billing figures ($481.25 memory, $189.28 active CPU, $141.69 edge requests) cover approximately the first two weeks of the current cycle; monthly figures are a 2× linear extrapolation and assume steady traffic.
  3. Request volume (~160M/mo) is derived from the edge-request charge: $141.69 ÷ $2 per million ≈ 71M billable + 10M plan-included over ~2 weeks, doubled.
  4. The request-mix split (heartbeats vs pageviews vs script fetches) is modeled from widget behavior (~10 heartbeats per ~5-minute session, 1 pageview + 1–2 script fetches per session) — it is an estimate, not a measurement. Vercel's per-path Observability view can confirm it precisely.
  5. Average function wall-clock (~1s) is inferred from the memory-to-request ratio; per-route timings should be confirmed in Vercel Observability before and after each change.
  6. Savings ranges are midpoint estimates; the before/after chart shows midpoints of those ranges. All prices are Vercel Pro list prices as of June 2026 (memory $0.0106/GB-hr, active CPU ~$0.128/hr, edge requests $2/M, builds $0.0035/CPU-min).
  7. Cron risk assessments are based on per-job code review: webhook coverage, lookback windows, and early-exit behavior were checked individually in the route handlers.
