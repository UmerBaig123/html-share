A2

GHL webhooks — stop rewriting unchanged rows

3 million pointless writes a day, gone.
Low risk
lastSyncedAt writes / day
Before
2,991,832
After
~50–100 K

What we changed

  • Switched an existence check from a scan (findFirst) to a direct key lookup (findUnique) on the tag's unique (contactId, tagDefId) key.
  • Only refresh the "last synced" timestamp when it's actually stale (>6h) instead of on every single webhook.

Why it's low-risk

  • We confirmed nothing in either codebase reads that timestamp — it's pure bookkeeping.
  • Tag data itself is unaffected; only the redundant timestamp write is throttled.
  • File: src/utils/ghl.utils.ts
How we know it's a no-op — and why it costs nothing extra. This fix does not compare tag content. Every webhook re-sends the same tags a contact already has, and the old code rewrote the lastSyncedAt timestamp on that row every single time — ~3M writes/day that changed nothing meaningful. Now we read the one row by its exact key (which the old code was already doing) and simply check the timestamp we just fetched: if it's fresh (<6h), we skip the write entirely. No new query — same single-row read as before, we just look at a column we already had in hand and decide not to write. A skipped write is pure savings: a write maintains the row's indexes and the redo log; a read we were already doing is free.

What we changed

  • All time windows and batch sizes kept identical.

Why it's low-med risk

  • Provably returns the same set of rows (the two branches don't overlap; we re-sort and take the same top 100).
  • Only the query shape changed, not the logic. File: meta-capi-retry/route.ts

What this code does

This cron is the safety net for Meta’s Conversions API. Every 5 minutes it finds conversion events that should have been sent to Meta but weren’t — either metaCapiStatus is null (never sent) or stuck on 'pending' — grabs the newest 100, and re-sends them.

What changed & why

It asked for both status classes in one query with an OR. MySQL can’t serve an OR across two different metaCapiStatus values (each with its own date window) from the (businessId, metaCapiStatus, createdAt) index — so every run fell back to scanning 7–16 million rows (~15 min). We split it into two separate queries, each a clean indexed range, then merge + dedupe + re-sort in memory. Same top-100 result, thousands of rows scanned instead of millions.

src/app/api/cron-jobs/meta-capi-retry/route.ts Before 
const unsent = await prisma.conversionEntry.findMany({
  where: {
    businessId: { in: businessIds },
    contactId: { not: null },
    OR: [
      { metaCapiStatus: null,      createdAt: { gte: lookbackThreshold, lte: graceThreshold } },
      { metaCapiStatus: 'pending', createdAt: { gte: lookbackThreshold, lte: pendingStuckThreshold } },
    ],
  },
  select: { id: true, businessId: true, conversionConfigId: true },
  orderBy: { createdAt: 'desc' },
  take: BATCH_SIZE,
});
After 
// One clean, indexable range query per status class — run in parallel.
const [neverSent, stuckPending] = await Promise.all([
  prisma.conversionEntry.findMany({
    where: { businessId: { in: businessIds }, contactId: { not: null },
             metaCapiStatus: null,
             createdAt: { gte: lookbackThreshold, lte: graceThreshold } },
    select: { id: true, businessId: true, conversionConfigId: true, createdAt: true },
    orderBy: { createdAt: 'desc' }, take: BATCH_SIZE,
  }),
  prisma.conversionEntry.findMany({
    where: { businessId: { in: businessIds }, contactId: { not: null },
             metaCapiStatus: 'pending',
             createdAt: { gte: lookbackThreshold, lte: pendingStuckThreshold } },
    select: { id: true, businessId: true, conversionConfigId: true, createdAt: true },
    orderBy: { createdAt: 'desc' }, take: BATCH_SIZE,
  }),
]);

// Merge, dedupe by id (a row can flip null -> 'pending' between the two
// snapshots and land in both -> without this it could be sent to Meta twice),
// re-sort newest-first, take the same top 100 the old query would have.
const seenIds = new Set<string>();
const unsent = [...neverSent, ...stuckPending]
  .filter((row) => (seenIds.has(row.id) ? false : (seenIds.add(row.id), true)))
  .sort((a, b) => b.createdAt.getTime() - a.createdAt.getTime())
  .slice(0, BATCH_SIZE);

What we changed

Why it's low-risk

What this code does — part 1: webhook sources list

Returns the list of webhook conversion sources for a business (used by the tracking / dashboard UI). It fetched the list with one findMany, then looped over it firing a raw SQL query per row just to read webhookPath — a workaround for a Prisma bug fixed long ago. Confirmed against the schema: webhookPath is a nullable scalar on ConversionSource and is written by the Typeform/Tally routers and others, so the findMany already returns it. Deleting the loop yields byte-identical output with zero extra queries.

What this code does — part 2: drip-campaign stats (admin)

The superadmin drip-campaign list shows, per campaign, total enrolled users and how many converted. It ran two count queries per campaign (2×N). One groupBy gets every count at once; the totals are derived in memory — provably the same numbers.

// Two count() queries per campaign  ->  2 x N queries.
const campaignsWithStats = await Promise.all(
  campaigns.map(async (campaign) => {
    const totalEnrolled = await prisma.userDripProgress.count({
      where: { campaignId: campaign.id } });
    const converted = await prisma.userDripProgress.count({
      where: { campaignId: campaign.id, status: 'CONVERTED' } });
    return { ...campaign, stats: { totalEnrolled, converted, /* ... */ } };
  })
);
After 
// One grouped query for ALL campaigns; totals derived in memory.
const progressBuckets = await prisma.userDripProgress.groupBy({
  by: ['campaignId', 'status'],
  where: { campaignId: { in: campaigns.map((c) => c.id) } },
  _count: { _all: true },
});

const statsByCampaign = new Map<string, { total: number; converted: number }>();
for (const bucket of progressBuckets) {
  const entry = statsByCampaign.get(bucket.campaignId) ?? { total: 0, converted: 0 };
  entry.total += bucket._count._all;                                 // total enrolled = sum of all status buckets
  if (bucket.status === 'CONVERTED') entry.converted += bucket._count._all;
  statsByCampaign.set(bucket.campaignId, entry);
}

const campaignsWithStats = campaigns.map((campaign) => {
  const { total: totalEnrolled = 0, converted = 0 } = statsByCampaign.get(campaign.id) ?? {};
  return { ...campaign, stats: { totalEnrolled, converted, /* ... */ } };
});

C1

Meta sync diff-writes — only write ads that changed

The biggest single item in the database: 5.9M "UPDATE ads"/day, most of them no-ops.
Medium risk
"UPDATE ads" / day (9.1% of all DB time)
Before
5,928,023 (all rows, changed or not)
After
thousands (only changed)

What we changed

  • Before writing, compare Meta's "last updated" + status against what we already have stored; skip rows that didn't change.
  • New rows are bulk-created; changed rows updated; unchanged rows left alone entirely.
  • Pure logic lives in src/lib/facebook/sync-diff.ts with unit tests.

Why it's safe

  • This is the only fix that changes what gets written, so the "did it change?" test is deliberately conservative — if Meta's updated_time or status moved at all, we write.
  • STEP 3 of the sync (the status-reconciliation pass) still runs unchanged and remains the authoritative healer for any status drift.
  • Every run logs created / updated / skipped counts, so the skip rate is observable in production.
How we detect an "unchanged" ad — without re-reading the whole ad. Meta stamps every campaign, ad set, and ad with an updated_time that moves whenever any field on it changes — name, budget, creative, status, anything. We store that stamp. On each sync we compare two tiny values: Meta's updated_time vs. our saved platformUpdatedTime, and Meta's effective_status vs. our saved status. If both match, nothing changed → skip the write. (We check status separately because a parent pausing can flip a child's effective status without bumping the child's own updated_time.) We never have to read the heavy fields — creativeData, cachedPreview — to decide.
"But doesn't comparing cost MORE database than before?" — No, it's dramatically less. Three reasons:
  • The comparison is free. It happens in app memory (two timestamps, two strings). Zero database work.
  • The read is tiny and we were already doing it. To compare, we fetch just 4 small indexed columns per row (id, platform id, updated_time, status) — no JSON blobs. The old path already read these rows to resolve parent relationships, and Prisma's upsert itself runs a SELECT before every UPDATE. We're not adding a meaningful read; we're reusing one.
  • We delete millions of WRITES. A write is far more expensive than a read: it rewrites the row, appends to the redo/undo logs, and updates every secondary index on the table (the ads table has ~7). A read of a few small indexed columns is served from memory. We trade one small batched read for ~5.9M eliminated UPDATE statements a day — net database work drops massively.
In short: reads are cheap and mostly already happening; the writes were the expensive part, and that's exactly what we stop.

What this code does

sync-optimized.ts is the hourly Meta ads sync: it pulls every campaign, ad set, and ad from the Meta API and writes them to our DB. The old code upsert-ed every row on every run — even rows identical to what was already stored. That is the single biggest item in the whole database: ~5.9M “UPDATE ads” per day, 9.1% of all DB time, rewriting rows that hadn’t changed.

What changed & why

A new module (src/lib/facebook/sync-diff.ts) decides per row whether Meta’s version differs from ours, using two tiny values Meta already gives us — updated_time and effective_status. Unchanged rows are skipped, new rows bulk-created, only genuinely-changed rows get an UPDATE. This is now the default write path for the sync.

src/lib/facebook/sync-diff.ts (new file — the decision logic) New module 
// The "did it change?" test: two tiny comparisons, no DB, no JSON blobs.
export function fbEntityChanged(fb: FbSyncEntity, existing: ExistingEntityState): boolean {
  const metaUpdatedMs = new Date(fb.updated_time).getTime();
  const metaEffectiveStatus = fb.effective_status || fb.status;
  return existing.platformUpdatedTime.getTime() !== metaUpdatedMs
      || existing.effectiveStatus !== metaEffectiveStatus;
}

// Bucket every Meta row into create / update / skip vs. what we already stored.
export function diffFbEntities<T extends FbSyncEntity>(
  fbRows: T[], existing: Map<string, ExistingEntityState>, keyFn: (row: T) => string | null
): FbEntityDiff<T> {
  const toCreate: T[] = [], toUpdate: Array<{ dbId: string; row: T }> = [];
  let skipped = 0, unmapped = 0;
  for (const row of fbRows) {
    const key = keyFn(row);
    if (key === null) { unmapped++; continue; }
    const current = existing.get(key);
    if (!current) { toCreate.push(row); continue; }
    if (fbEntityChanged(row, current)) toUpdate.push({ dbId: current.id, row });
    else skipped++;
  }
  return { toCreate, toUpdate, skipped, unmapped };
}
